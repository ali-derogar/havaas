# نصب و نگهداری PWA حواس

حواس دارای مانیفست فارسی، آیکن‌های ۱۹۲ و ۵۱۲ پیکسلی، آیکن maskable، آیکن آیفون و حالت اجرای مستقل است. در مرورگرهای پشتیبان، برنامه از بخش «حساب من» یا منوی نصب مرورگر قابل نصب است. در آیفون و آیپد، از Safari، دکمهٔ اشتراک‌گذاری و سپس «افزودن به صفحهٔ اصلی» استفاده کنید. راهنمای نصب متناسب با دستگاه در صفحهٔ حساب نمایش داده می‌شود.

برای نصب از روی دامنه، HTTPS لازم است؛ `localhost` و آدرس loopback برای توسعه قابل استفاده‌اند. نصب در حالت خصوصی Chrome در دسترس نیست. [راهنمای نصب PWA در MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

## اتصال و آفلاین

- پس از اولین دریافت موفق، فایل‌های رابط، قلم، آیکن‌ها، جهان‌های SVG فعلی و راهنمای صوتی کش می‌شوند. تصاویر قدیمیِ نقاشی‌شده که در هفت بازی فعلی استفاده نمی‌شوند به دانلود اولیهٔ نصب اضافه نمی‌شوند.
- اجرای مجدد بدون اتصال، صفحهٔ فارسیِ آفلاین را نشان می‌دهد. دکمهٔ «تلاش دوباره» دسترسی واقعی به مرکز را بررسی می‌کند؛ اتصال دستگاه به شبکه به‌تنهایی به معنی دسترسی به سرور نیست.
- ورود، شروع جلسه، دریافت گزارش و ثبت نتیجه به اتصال مرکز نیاز دارند. درخواست‌های `/api`، خروجی گزارش، حساب‌ها و همهٔ عملیات نوشتن از کش و صف ارسال خودکار کنار گذاشته شده‌اند.
- بازیِ از قبل بازشده می‌تواند هنگام قطعی ادامه یابد. اگر نتیجه هنوز ثبت نشده، صفحه را نبندید و پس از اتصال از «تلاش دوباره برای ثبت» استفاده کنید. نگهداری نتیجه تا بستن صفحه، همان رفتار موجود برنامه است؛ PWA نتیجه را به‌عنوان ثبت‌شده نمایش نمی‌دهد.

## ساخت و انتشار

```sh
npm run build
npm start
```

ساخت، `dist/sw.js` را با شناسه‌ای حاصل از محتوای نسخه تولید می‌کند. تغییر فایل‌های رابط یا دارایی‌های کش‌شده، شناسه را خودکار عوض می‌کند و نیازی به تغییر دستی شمارهٔ کش نیست. آیکن‌ها و `manifest.webmanifest` و `offline.html` نیز داخل خروجی ساخت قرار می‌گیرند. سرور Node و تصویر Docker مسیرهای لازم و نوع محتوای درست را ارائه می‌کنند. `npm run static` این فایل‌ها را برای بررسی محلی ارائه می‌کند و همچنان جای API برنامه را نمی‌گیرد.

در صورت استفاده از پراکسی، مسیرهای `/sw.js`، `/manifest.webmanifest`، `/offline.html`، `/assets/` و `/src/` باید به همین خروجی/سرور برسند. پاسخ `/sw.js` باید `Cache-Control: no-cache` و `Service-Worker-Allowed: /` داشته باشد. `/api/` و `/health` باید به سرور برسند. سیاست CSP سرور فقط worker و manifest هم‌مبدأ را مجاز می‌کند.

## به‌روزرسانی

نسخهٔ جدید ابتدا کامل دانلود می‌شود؛ دانلود ناقص جای نسخهٔ فعال را نمی‌گیرد. رابط و کد هر صفحه از یک نسخهٔ یکسان خوانده می‌شوند. پس از آماده‌شدن نسخه، پیام «به‌روزرسانی» نمایش داده می‌شود. وسط بازی این پیام روی میدان قرار نمی‌گیرد.

پیش از اعمال به‌روزرسانی، تمام پنجره‌های باز باید آماده باشند. اجرای بازی، نتیجهٔ ثبت‌نشده، شروع جلسه، ارسال فرم، پنجرهٔ محاوره‌ای یا تغییرات ذخیره‌نشدهٔ فرم مانع اعمال نسخه می‌شوند. خارج‌شدن فوکوس از فیلد، تغییرات ذخیره‌نشده را پاک نمی‌کند. وضعیت فرم پس از ذخیرهٔ موفق یا بازگرداندن مقادیر اولیه پاک می‌شود؛ فرمِ لغوشده در پنجرهٔ بسته، به‌روزرسانی را قفل نمی‌کند. وضعیت اولیه بعد از مقداردهی فیلدها با جاوااسکریپت ثبت می‌شود تا فرم دست‌نخورده به‌اشتباه ویرایش‌شده تلقی نشود. محتوای فرم فقط در حافظهٔ همان صفحه می‌ماند و به worker یا کش فرستاده نمی‌شود.

وقتی پنجره‌ها آماده شدند، موقتاً ورودی آن‌ها بسته می‌شود. درست پیش از فعال‌کردن نسخه، فهرست پنجره‌ها دوباره بررسی می‌شود؛ اگر پنجرهٔ تازه‌ای باز شده باشد، درخواست لغو و ورودی پنجره‌های آماده آزاد می‌شود. پس از فعال‌شدن نسخهٔ جدید، پنجره‌ها دوباره بارگذاری می‌شوند. در صورت رد یا قطع فرایند نیز ورودی‌ها آزاد می‌شوند. کش نسخهٔ قبلی پس از فعال‌شدن نسخهٔ جدید پاک می‌شود؛ کش برنامه‌های دیگر دست‌نخورده می‌ماند.

هنگام ارسال فرم، فیلدها و دکمه‌ها موقتاً غیرفعال می‌شوند تا مقدارِ در حال ثبت با ویرایش تازه تداخل نکند. پس از موفقیت یا خطا، وضعیت قبلی هر کنترل برمی‌گردد. خطای اعتبارسنجی یا خطای سرور، وضعیت تغییرات ذخیره‌نشده را پاک نمی‌کند.

## بررسی

```sh
node --test tests/pwa.test.mjs
npx playwright test tests/browser/pwa.spec.mjs
npm run test:docker
```

تست‌ها شامل شناسهٔ نسخه و کش اتمی، کنارگذاشتن اطلاعات حساب از کش، درخواست محدودهٔ بایتی صدا، مسیرهای عمومی و CSP، نصب‌پذیری واقعی Chrome با پروفایل موقت عادی، بازشدن آفلاین و اتصال دوباره، راهنمای نصب و تأیید نصب مرورگر، و به‌روزرسانی دو پنجره هنگام بازی و انتظار برای ثبت نتیجه هستند. تست Docker وجود فایل‌های PWA در تصویر ساخته‌شده و حفظ ورود و نتایج پس از راه‌اندازی دوباره را نیز بررسی می‌کند.

بازبینی تکمیلی، فرم ویرایش‌شدهٔ بدون فوکوس، بازشدن پنجرهٔ تازه در میانهٔ بررسی آماده‌بودن، ذخیرهٔ موفق و شکست‌خورده، تأخیر پاسخ ذخیره، لغو فرم پنجرهٔ محاوره‌ای و مقداردهی اولیه و ذخیرهٔ تنظیمات سطح را نیز پوشش می‌دهد. آزمون‌های به‌روزرسانی، انتشار نسخه را فقط در سرور موقت E2E شبیه‌سازی می‌کنند و فایل آزمایشی در پوشهٔ دارایی‌های پروژه نمی‌سازند.

تصویرهای بررسی: `.local/verification/pwa-install-360.png` و `.local/verification/pwa-offline.png`.

نتیجهٔ اجرای اولیهٔ PWA: ۳۰۴ تست منطق و رابط، ۳۷ تست واقعی API و تمام ۱۰۴ سناریوی مرورگر موفق شدند. ساخت و آزمون کامل Docker، مسیرهای PWA در سرور استاتیکِ منبع و خروجی ساخت، یکسان‌بودن نسخهٔ worker این دو، بررسی نحوی و `git diff --check` هم موفق بودند. گزارش‌ها در `.local/pwa-unit-final.log`، `.local/pwa-api-final.log`، `.local/pwa-browser-final.log`، `.local/pwa-docker-final.log` و `.local/pwa-static-check.log` قرار دارند.

نتیجهٔ بازبینی تکمیلی: تمام ۳۱۰ تست منطق و رابط، ۳۷ تست واقعی API و ۱۰۹ سناریوی مرورگر موفق شدند. ساخت، آزمون کامل Docker، یکسان‌بودن worker ساخته‌شده با سورس فعلی و وجود ماژول حفاظت فرم در کش نسخه نیز تأیید شد. فایل موقت آزمون در دارایی‌های خروجی وجود ندارد. بررسی نحوی و بررسی فاصله‌های تغییراتِ آماده‌شده و آماده‌نشده نیز موفق بودند. گزارش‌ها در `.local/pwa-audit-unit-final.log`، `.local/pwa-audit-api-final.log`، `.local/pwa-audit-browser-final.log` و `.local/pwa-audit-docker-final.log` قرار دارند.
